域环境搭建

最近尝试着用 ai 做了一个渗透测试 agent，项目地址在：

https://github.com/Change444/AttackAgent#%E4%B8%AD%E6%96%87

这篇文章不想写成项目介绍，因为 AttackAgent 当前的能力其实还很差，架构也还有很多混杂的地方。如果只是把模块列一遍，写 Manager、Solver、Memory、ToolBroker、Web UI，看起来会像一个完成度很高的平台，但那不是事实。

我更想把它写成一次技术复盘：做完这个项目之后，我对“渗透测试 agent 到底应该怎么设计”有了一些新的理解。哪些思路是对的，哪些地方走偏了，哪些东西值得继续做，哪些东西应该推倒重来，这些比单纯介绍项目更有价值。

为什么做这个项目？

起因是刷到了淚笑师傅腾讯黑客松智能渗透大赛的那篇文章，最近正好在学习 ai，心血来潮想着能不能靠自己开发一个 agent。

一开始想了两种方向。

第一种是 Sub-agent 的思路，给每类漏洞安排一个子 agent，比如 SQL 注入 agent、SSRF agent、反序列化 agent，由主 agent 判断目标漏洞类型，然后调用对应子 agent 去解决。

这种方式看起来很合理，但我很快就 pass 掉了。

原因不是它实现不了，而是我觉得它从设计上就限制了 ai 的能力。渗透测试不是一个特别规整的流程，很多题看起来像 web，中间可能要做编码、协议、源码审计，甚至还要结合系统层面的知识。如果一开始就把 ai 按漏洞类型拆成固定角色，看似职责清晰，本质上也是提前给它画了边界。

我想要的不是一组固定角色，而是给 ai 尽量大的思考空间。它应该能自己判断当前要侦察、验证、回头看上下文，还是切换方向。换句话说，我理想中的渗透测试 agent 应该是：

所以我选择了第二种方向：启发式推导 + 原语动作。

原语动作就是渗透测试里最基本的能力，比如发送 HTTP 请求、浏览器检查、结构化解析、编码解码、文件分析、候选 flag 提取等。我的想法是不要先规定 ai 是哪个漏洞类型的专家，而是给它一组基础能力，让它根据上下文自己组合。

但问题也出在这里：只给工具是不够的。

ai 有了手，但还需要脑子。这个“脑子”不是模型本身，而是上下文连续性、策略层、记忆机制和反馈机制。AttackAgent 最大的问题，也恰恰出在这些地方。

我理解的渗透测试 Agent

做这个项目之前，我对 agent 的理解还是偏“工具调用”：让模型能调用 HTTP、浏览器、解析、沙盒这些工具，然后循环执行，直到拿到 flag。

做完之后我才意识到，渗透测试 agent 的核心并不是工具数量，而是能不能保持一个连续的攻击上下文。

渗透测试和普通问答不一样。普通问答可以一问一答结束，但渗透测试是一连串观察、假设、验证、失败、修正、再验证的过程。前一步拿到的 cookie、token、路径、报错、源码片段、失败 payload，都会影响下一步。

如果太自由，ai 会发散，可能不断尝试低价值动作，也可能忘记前面已经失败过的路径。如果太约束，ai 又会变成一个套模板的自动化脚本。真正难的是中间状态：让它能自由思考，但每一步都被上下文轻轻拉住。

这也是为什么我一开始不想做 Sub-agent。按漏洞类型拆 agent，本质上是通过角色预设限制思考空间。我更希望 ai 拿到的是一组底层能力，然后根据上下文自己决定组合方式。

但后面踩坑之后我发现，仅仅给原语也不够。原语给的是手，上下文才是脑子。如果上下文连续性做不好，ai 就会变成一个每轮都重新看题的人；工具再多，也只是更多可调用按钮。

上下文连续性才是核心

我现在觉得，渗透测试 agent 最重要的不是“会调用多少工具”，而是上下文能不能连续。

Manager 的初衷和问题

我设置 Manager 的初衷，是希望系统里有一个“决策者”能主导渗透测试过程。

因为渗透测试本身就是一个连贯过程，不应该每轮都让模型从零开始判断。Manager 应该像一个渗透测试人员一样，知道当前阶段是什么，前面尝试过什么，哪些证据可靠，哪些方向已经走不通，下一步为什么值得做。

原因在于，Manager 最后更像一个状态机，而不是真正的渗透决策者。它读到的上下文质量不够高，Memory 也没有真正变成强约束，所以很多决策还是依赖 prompt 里的摘要信息。

这就回到了前面那个问题：我做了一个“决策者”的外壳，但没有给它足够好的记忆和判断依据。

所以如果重新做，我会先设计记忆机制，再设计 Manager。Manager 可以有，但它应该建立在高质量、结构化、可查询、可推理的记忆之上。否则 Manager 只是读一堆整理过的 prompt，然后做状态机判断，本质上没有真正主导渗透过程。

自由和约束的平衡

一开始我拒绝 Sub-agent，是因为不想限制 ai 的能力。

但比较讽刺的是，项目越写越复杂之后，我又在无形之中给 ai 加了很多约束：Manager 的状态机、Policy 的门禁、Observer 的干预、Memory 的压缩方式、Review Gate 的审批逻辑。

这些模块的初衷都是好的：让 agent 不要乱跑，不要重复失败，不要越权执行，不要提交错误结果。

但如果设计不好，它们也会反过来限制 ai 的探索空间。

这让我意识到，渗透测试 agent 不是约束越少越好，也不是约束越多越安全，而是要把约束放在正确的位置。

这是我觉得 Sub-agent 架构最大的问题：它把约束放在了思考层，而不是执行层。

值得保留的设计

虽然 AttackAgent 当前能力不强，但有些设计我觉得还是值得保留的。

1. 原语动作

原语动作这个方向我仍然认可。

相比给每类漏洞写一个 agent，原语更接近渗透测试的底层能力。它不会提前限制 ai 的判断，而是提供一组可以自由组合的动作。

后续要做的是增强原语能力，而不是放弃这个方向。比如浏览器交互、认证态保持、文件上传下载、压缩包分析、源码项目分析、漏洞链路验证，这些都应该继续补。

2. 事件流

Blackboard 这种事件流设计也值得保留。

因为 agent 不是一次性脚本，它需要能解释自己为什么做这一步，也需要能在失败后回放整个过程。事件流能让 Manager、Memory、Observer、Replay 都消费同一份事实来源。

但这里要注意，事件语义必须干净。早期我把 idea、converge、candidate flag 都混在类似事件里，结果后面的状态判断和提交逻辑都会被污染。这个教训很深。

3. Policy 和 Review

Policy 和 Review 也值得保留，但它们应该是执行层的安全边界，而不是思考层的枷锁。

高风险动作、提交 flag、可能产生副作用的操作，应该经过策略检查和人工确认。但这种约束不应该影响模型探索漏洞方向，否则就会从安全控制变成思维限制。

4. Replay

Replay 不是锦上添花。

如果一个 agent 失败了，我需要知道它为什么失败，是工具能力不够，还是上下文丢了，还是策略层判断错了，还是模型在重复低价值动作。没有 Replay，就只能看到最后一句 failed，这对调试 agent 没有意义。

最大的失败教训

这次做完之后，我觉得最大的失败不是“能力弱”。

能力弱可以补。缺浏览器能力，就补浏览器；缺文件分析，就补文件分析；缺利用链，就补更细的原语。这些是工程量问题。

真正麻烦的是策略层和记忆机制设计错了。

因为策略层一旦锚定，后面的模块都会围绕它生长。你一开始选择的是 prompt 注入式上下文，后面 Manager、Memory、Observer、ToolBroker 都会围着这个方式适配。等你意识到这不是一个真正连续的记忆系统时，整个项目已经长出很多依赖，重构成本就会非常高。

这也是我现在最大的体会：

AttackAgent 最大的问题就是没有把 Memory 设计成策略层的核心，而是把它做成了 prompt 摘要工具。这样系统看起来有记忆，但本质上还是在赌模型能不能读懂下一轮 prompt。

这和我理想中的渗透测试 agent 是有差距的。

我想要的是一个上下文连续的 agent，而不是一个每轮重新读摘要的 prompt agent。

后续如果重做

如果后面继续做，我会调整优先级。

第一，不急着做多 Solver，也不急着继续扩展 Web UI，而是先把单 Solver 的连续上下文打磨好。

第二，重做记忆机制。Memory 不能只是事件摘要，而应该成为策略层的核心输入。它要能沉淀失败边界、成功路径、关键事实、上下文依赖，而不是只把最近几条 observation 压缩后塞进 prompt。

第三，明确事实来源。StateGraph 和 Blackboard 不能长期混着用，必须明确谁是 runtime 的真实状态源。

第四，增强原语能力。浏览器、认证态、文件分析、源码分析、漏洞链路验证，这些底层能力要补上，否则策略层设计再好也没有足够动作可以执行。

第五，建立真实靶场回归集。不要只看单元测试和 acceptance test，而是要看真实题目的成功率、失败原因、耗时、重复尝试次数、错误提交次数。

第六，等单 Solver 真正稳定之后，再考虑多 Solver 协作。多个弱 Solver 并不会变成一个强系统，只会把状态和调度问题放大。

总结

如果用一句话总结这次复盘，我觉得是：

Sub-agent 的问题是太早限制了 ai 的思考空间；纯原语动作的问题是如果没有好的记忆和策略层，ai 又会失去方向。

所以好的渗透测试 agent 应该在三者之间找到平衡：

AttackAgent 目前还没有做到这一点。它更像一个把很多想法拼起来的原型，能力弱、架构混杂、记忆机制也没有真正做好。

但它至少让我想清楚了一件事：能力可以慢慢补，原语可以慢慢扩展，但策略层和记忆机制一旦锚定错了，后面会非常难改。

这可能才是这次开发里最重要的收获。
