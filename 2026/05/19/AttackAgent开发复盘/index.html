AttackAgent开发复盘

2026-05-19 5k post.wordcount 42 post.min2read AI #agent开发

最近尝试着用 AI 做了一个渗透测试 agent，项目地址在：

https://github.com/Change444/AttackAgent#%E4%B8%AD%E6%96%87

这篇文章不想写成项目介绍，因为 AttackAgent 当前的能力其实还很差，架构也还有很多混杂的地方。如果只是把模块列一遍，写 Manager、Solver、Memory、ToolBroker、Web UI，看起来会像一个完成度很高的平台，但那不是事实。

我更想把它写成一次技术复盘：做完这个项目之后，我对”渗透测试 agent 到底应该怎么设计”有了一些新的理解。哪些思路是对的，哪些地方走偏了，哪些东西值得继续做，哪些东西应该推倒重来，这些比单纯介绍项目更有价值。

为什么做这个项目？

起因是刷到了淚笑师傅腾讯黑客松智能渗透大赛的那篇文章，最近正好在学习 AI，心血来潮想着能不能靠自己开发一个 agent。

一开始想了两种方向。

第一种是 Sub-agent 的思路，给每类漏洞安排一个子 agent，比如 SQL 注入 agent、SSRF agent、反序列化 agent，由主 agent 判断目标漏洞类型，然后调用对应子 agent 去解决。

这种方式看起来很合理，但我很快就 pass 掉了。

原因不是它实现不了，而是我觉得它从设计上就限制了 AI 的能力。渗透测试不是一个特别规整的流程，很多题看起来像 web，中间可能要做编码、协议、源码审计，甚至还要结合系统层面的知识。如果一开始就把 AI 按漏洞类型拆成固定角色，看似职责清晰，本质上也是提前给它画了边界。

我想要的不是一组固定角色，而是给 AI 尽量大的思考空间。它应该能自己判断当前要侦察、验证、回头看上下文，还是切换方向。

所以我选择了第二种方向：启发式推导 + 原语动作。

原语动作就是渗透测试里最基本的能力，比如发送 HTTP 请求、浏览器检查、结构化解析、编码解码、文件分析、候选 flag 提取等。我的想法是不要先规定 AI 是哪个漏洞类型的专家，而是给它一组基础能力，让它根据上下文自己组合。

最初的大致流程是：连接靶场 → 调用原语信息搜集 → 将已知情报存储 → 注入 prompt → 询问 AI 下一步任务 → 执行下一步任务直到解出 flag。

现在回头看，这个方向我觉得还是对的。原语动作能最大化保留 AI 的组合空间，不会像 Sub-agent 那样一开始就把思路框死。

但问题也出在这里：只给工具是不够的。

自由探索与适度引导

做这个项目之前，我对 agent 的理解还是偏”工具调用”：让模型能调用 HTTP、浏览器、解析、沙盒这些工具，然后循环执行，直到拿到 flag。

做完之后我才意识到，渗透测试 agent 的核心并不是工具数量，而是能不能保持一个连续的攻击上下文。

渗透测试和普通问答不一样。普通问答可以一问一答结束，但渗透测试是一连串观察、假设、验证、失败、修正、再验证的过程。前一步拿到的 cookie、token、路径、报错、源码片段、失败 payload，都会影响下一步。

所以一个好的渗透测试 agent 至少要做到两点：

第一，给 AI 尽可能大的思考空间，不要被预设角色锁死。
第二，用上下文、证据和失败边界引导它，不要让它乱跑。

这两个目标其实是有张力的。

如果太自由，AI 会发散，可能不断尝试低价值动作，也可能忘记前面已经失败过的路径。如果太约束，AI 又会变成一个套模板的自动化脚本。真正难的是中间状态：让它能自由思考，但每一步都被上下文轻轻拉住。

这也是为什么我一开始不想做 Sub-agent。按漏洞类型拆 agent，本质上是通过角色预设限制思考空间。我更希望 AI 拿到的是一组底层能力，然后根据上下文自己决定组合方式。

但后面踩坑之后我发现，仅仅给原语也不够。原语给的是手，上下文才是脑子。 如果上下文连续性做不好，AI 就会变成一个每轮都重新看题的人；工具再多，也只是更多可调用按钮。

所以我的核心设计原则变成了：

思考层开放，策略层引导，执行层约束。

渗透测试 agent 不是约束越少越好，也不是约束越多越安全，而是要把约束放在正确的位置。安全边界应该卡在工具执行前，方向引导应该来自上下文，而不是一开始就给模型贴死角色标签。这也是我觉得 Sub-agent 架构最大的问题——它把约束放在了思考层，而不是执行层。

具体做了什么

基于上面的设计哲学，AttackAgent 做了几个核心模块来支撑”上下文连续性”。

事件流与记忆

我设计了两层架构：

  • Blackboard：保存完整事件流，负责可回放、可审计
  • Memory：从事件流里抽取结构化信息，负责下一轮真正要喂给 Solver 的上下文

每次工具执行后，系统会写入事件：OBSERVATION、ACTION_OUTCOME、CANDIDATE_FLAG、SECURITY_VALIDATION。

然后 MemoryReducer 从最近的事件里抽取结构化记忆：

  • FACT：普通事实，比如页面里发现了某个参数
  • CREDENTIAL：认证态，比如 cookie、auth header
  • ENDPOINT：接口、路径、目标地址
  • FAILURE_BOUNDARY：失败边界，比如某种 payload 已经失败
  • scratchpad_summary：给下一轮 Solver 用的短摘要
  • recent_event_ids：保留证据引用，方便 replay 和追溯

这里最有价值的是失败边界。很多 agent 会反复做同一个无效尝试，本质上就是没有把失败沉淀成约束。失败不是垃圾信息，失败应该变成下一轮推理的边界。

Manager

我设置 Manager 的初衷，是希望系统里有一个”决策者”能主导渗透测试过程。

Manager 拿到一个 ManagerContext——包含项目状态、Solver 会话、候选 flag、停滞点、失败边界、预算、Observer 报告等——然后根据上下文产出动作：

bootstrap 阶段发射 LAUNCH_SOLVER，reason 阶段转向 STEER_SOLVER，探索阶段有候选 flag 就 CONVERGE，连续失败或死路过多就 ABANDON 或 STEER，Observer 提醒异常就 THROTTLE、STOP、REASSIGN 或 ABANDON。

Policy、Review 与 Replay

高风险动作、提交 flag、可能产生副作用的操作，经过策略检查和人工确认。同时保留完整的事件流用于 Replay——如果 agent 失败了，我需要知道是工具能力不够、上下文丢了、策略层判断错了，还是模型在重复低价值动作。没有 Replay，就只能看到最后一句 failed，对调试 agent 没有意义。

做对了什么，做错了什么

做对的

原语动作这个方向我仍然认可。相比给每类漏洞写一个 agent，原语更接近渗透测试的底层能力，不会提前限制 AI 的判断。后续要做的是增强原语能力——浏览器交互、认证态保持、文件上传下载、压缩包分析、源码项目分析、漏洞链路验证，这些都应该继续补。

事件流也值得保留。Agent 不是一次性脚本，它需要能解释自己为什么做这一步，也需要能在失败后回放整个过程。事件流能让 Manager、Memory、Observer、Replay 都消费同一份事实来源。但这里要注意，事件语义必须干净。早期我把 idea、converge、candidate flag 都混在类似事件里，结果后面的状态判断和提交逻辑都会被污染。这个教训很深。

Policy 和 Review 作为执行层的安全边界是成立的。但这种约束不应该影响模型探索漏洞方向，否则就会从安全控制变成思维限制。

做错的

最大的失败不是”能力弱”。能力弱可以补。缺浏览器能力，就补浏览器；缺文件分析，就补文件分析；缺利用链，就补更细的原语。这些是工程量问题。

真正麻烦的是记忆机制设计错了。

AttackAgent 的 Memory 更像”记录”和”摘要”，而不是”经验”。很多地方只是把整理后的信息注入 prompt，然后希望模型下一轮自己接住上下文。表面上有 Memory、有 ContextCompiler、有 Manager，实际还是落回了 prompt 注入。

真正好的记忆机制不应该只是整理文本，而应该能影响策略层。它应该回答这些问题：

这个题更像哪类漏洞？之前类似题成功过的关键步骤是什么？某个失败边界是否只对当前参数有效？哪些观察是高价值，哪些只是噪音？下一个动作为什么比其他动作更值得尝试？

AttackAgent 还没有做到这一步。

这直接导致了 Manager 的问题。Manager 的初衷是做渗透决策者，但我做了一个”决策者”的外壳，却没有给它足够好的记忆和判断依据。它读到的上下文质量不够高，Memory 也没有真正变成强约束，所以很多决策还是依赖 prompt 里的摘要信息。最后 Manager 更像一个状态机，而不是真正的渗透决策者。

策略层一旦锚定，后面的模块都会围绕它生长。 你一开始选择的是 prompt 注入式上下文，后面 Manager、Memory、Observer、ToolBroker 都会围着这个方式适配。等你意识到这不是一个真正连续的记忆系统时，整个项目已经长出很多依赖，重构成本就会非常高。

这也是我现在最大的体会：

能力可以后期扩展，原语可以慢慢增强，UI 可以后面再做。但策略层和记忆机制一开始就要想清楚。

另外一个讽刺的地方是，我一开始拒绝 Sub-agent，是因为不想限制 AI 的能力。但项目越写越复杂之后，我又在无形之中给 AI 加了很多约束：Manager 的状态机、Policy 的门禁、Observer 的干预、Memory 的压缩方式、Review Gate 的审批逻辑。这些模块的初衷都是好的，但如果设计不好，它们也会反过来限制 AI 的探索空间。

当前问题和后续方向

这里简单说一下 AttackAgent 的现状。

它现在有 Team Runtime、Blackboard、ToolBroker、Memory、Review、Observer、Web UI 等模块，但整体还是混杂状态：

  • StateGraph 和 Blackboard 事实来源不够统一
  • 旧规划器和新 Team Runtime 之间还有历史包袱
  • Memory 只是初步结构化，没有真正形成经验系统
  • Manager 更像状态机，不像真正的渗透决策者
  • 原语能力还比较弱，复杂题目支撑不起来
  • 多 Solver 协作还没有真实证明
  • 测试不少，但端到端真实靶场回归不足

这些问题说明一件事：模块多不代表能力强。

有一段时间我太依赖”补模块”解决问题。遇到记忆问题，就加 Memory；遇到协作问题，就加 MergeHub；遇到不可观察，就加 Web UI；遇到风险控制，就加 Policy 和 Review。每个模块单独看都有意义，但模块越加越多之后，系统复杂度也同步放大。最后项目变成了：功能点很多、概念很多、测试很多、文档很多，但真实解题能力没有按比例提升。

这其实是做 agent 项目很容易踩的坑。agent 项目不是概念堆叠比赛，最终还是要看能不能稳定解决问题。

如果后面继续做，我会调整优先级：

  1. 先打磨单 Solver 的连续上下文，不急着做多 Solver，也不急着继续扩展 Web UI
  2. 重做记忆机制，Memory 不能只是事件摘要，而应该成为策略层的核心输入，要能沉淀失败边界、成功路径、关键事实、上下文依赖
  3. 明确事实来源，StateGraph 和 Blackboard 不能长期混着用，必须明确谁是 runtime 的真实状态源
  4. 增强原语能力，浏览器、认证态、文件分析、源码分析、漏洞链路验证，这些底层能力要补上，否则策略层设计再好也没有足够动作可以执行
  5. 建立真实靶场回归集，不要只看单元测试和 acceptance test，而是要看真实题目的成功率、失败原因、耗时、重复尝试次数、错误提交次数
  6. 等单 Solver 真正稳定之后，再考虑多 Solver 协作，多个弱 Solver 并不会变成一个强系统，只会把状态和调度问题放大

总结

如果用一句话总结这次复盘，我觉得是：

渗透测试 agent 的核心不是工具调用，而是上下文连续性驱动下的自由探索。

Sub-agent 的问题是太早限制了 AI 的思考空间；纯原语动作的问题是如果没有好的记忆和策略层，AI 又会失去方向。

所以好的渗透测试 agent 应该在三者之间找到平衡：思考层开放，策略层引导，执行层约束。

AttackAgent 目前还没有做到这一点。它更像一个把很多想法拼起来的原型，能力弱、架构混杂、记忆机制也没有真正做好。但它至少让我想清楚了一件事：能力可以慢慢补，原语可以慢慢扩展，但策略层和记忆机制一旦锚定错了，后面会非常难改。

这可能才是这次开发里最重要的收获。
