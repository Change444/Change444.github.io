初识智能体

什么是智能体

在人工智能领域，智能体被定义为任何能够通过传感器（Sensors）感知其所处环境（Environment），并自主地通过执行器（Actuators）采取行动（Action）以达成特定目标的实体。 这是最宽泛的定义

而在以GPT（Generative Pre-trained Transformer为代表的大语言模型的出现以后，与之相应的出现了由大语言模型驱动的 LLM 智能体，他们有如下特征：

  1. 规划与推理：智能体首先会将这个高层级目标分解为一系列逻辑子任务
  2. 工具使用：在执行规划时，智能体识别到信息缺口，会主动调用外部工具来补全
  3. 动态修正：在交互过程中，智能体会将用户的反馈视为新的约束，并据此调整后续的行动

智能体的构成与运行原理

了解智能体的运作前，我们应先了解他的任务环境。在人工智能领域，通常使用PEAS 模型来精确描述一个任务环境，即分析其性能度量(Performance)、环境(Environment)、执行器(Actuators)和传感器(Sensors) 。例如，一个渗透测试场景用PEAS模型是这么表示的：

  1. Performance：在有限的时间内，最快的挖出漏洞
  2. Environment：各种web网站，内网环境等
  3. Actuators：bash，扫描器，漏洞利用工具等
  4. Sensors：工具返回的结果，网站的回显，用户的指令，漏洞的相关情报等

智能体主要由感知、推理、行动和记忆四大核心部分构成，通过自我闭环机制自主完成任务。它并非一次性完成任务，而是通过一个持续的循环与环境进行交互，这个核心机制被称为 智能体循环 (Agent Loop)，如图所示

行动并非循环的终点。智能体的行动会引起环境 (Environment) 的状态变化 (State Change)，环境随即会产生一个新的观察 (Observation) 作为结果反馈。这个新的观察又会在下一轮循环中被智能体的感知系统捕获，形成一个持续的”感知-思考-行动-观察”的闭环。智能体正是通过不断重复这一循环，逐步推进任务，从初始状态向目标状态演进。

为了让 LLM 能够有效驱动这个循环，我们需要一套明确的交互协议 (Interaction Protocol) 来规范其与环境之间的信息交换。这一协议体现在对智能体每一次输出的结构化定义上，智能体的输出不再是单一的自然语言回复，而是一段遵循特定格式的文本，这一文本通常包括思考和行动两个部分，例如：

action字段是大模型基于推理得出来的动作，这一动作将被解析器 (Parser) 接受并调用对应函数（或工具），返回的结果经过Observation（观察者） 又将变为自然语言展示给用户，或者进入下一个Loop循环，例如：

与 Workflow 的差异：Workflow 是预先定义的结构化编排，步骤写死在代码里；Agent 是以目标为导向的自主系统，能根据实时信息动态推理和决策。
例如用户问”查一下今天北京天气，再推荐个景点”：

  • Agent 自主拆解为”查天气 → 推荐景点”两步，调用天气 API 获取”晴朗，微风”
  • 基于结果推理”晴天适合户外”，筛选出故宫、颐和园等推荐
    整个过程没有 if 天气=晴 then 推荐颐和园 的硬编码规则——这种基于实时信息进行动态推理和决策的能力，就是 Agent 的核心价值。

大语言模型基础

智能体经典范式构建

为了更好地组织智能体的”思考”与”行动”过程，当前业界主要有这三种架构范式：

  • ReAct (Reasoning and Acting)： 一种将”思考”和”行动”紧密结合的范式，让智能体边想边做，动态调整。
  • Plan-and-Solve： 一种”三思而后行”的范式，智能体首先生成一个完整的行动计划，然后严格执行。
  • Reflection： 一种赋予智能体”反思”能力的范式，通过自我批判和修正来优化结果。

ReAct

主要原理：智能体将不断重复Thought -> Action -> Observation 的循环，将新的观察结果追加到历史记录中，形成一个不断增长的上下文，直到它在Thought中认为已经找到了最终答案，然后输出结果。

最简单的实现方式是实现一个while循环，每次循环结尾会把工具调用和观察结果存入prompt用于下一次调用模型，直到解决问题，例如：

每循环一次，提示词就会自动添加上个循环的结果，当action出现Finish表示问题解决时，循环也就结束了。这样做的好处是智能体能根据每一步从外部世界获得的 Observation 来动态调整后续的 Thought 和 Action，同时天然地将大语言模型的推理能力与外部工具的执行能力结合起来。但是局限也很明显，主要有以下这几个方面的缺陷：

  1. 依赖LLM能力：推理、指令遵循、格式输出任一不足，整个流程就断
  2. 效率低：串行循环，步骤越多，耗时和费用越高，后期提示词会越来越长，若不加以调整会影响执行的结果甚至导致模型幻觉
  3. 提示词脆弱：模板措辞微变就影响行为，不同模型对格式遵循不稳定
  4. 缺乏全局视野：步进决策容易走局部最优，甚至原地打转

Plan-and-Solve

主要原理：先规划后执行，主要由Planner和Executor组成，Planner将一个大问题分解为多个阶段供Executor逐一执行，Executor会记录每一步的执行结果，并将其作为上下文提供给后续步骤，直到完成Planner给的任务。

Executor实现起来跟ReAct差不多，区别就是不用思考下一步做什么，规划的任务交由Planner来进行。个人感觉Plan-and-Solve算是ReAct的一种改进，但是这种架构范式依然存在问题，太过依赖于Planner，没有纠错机制，缺乏灵活性，难以应对计划外的变化

Reflection

Reflection主要是解决Planner生成规划没有纠错机制这一痛点，在生成方案后，进入反思-优化循环，锚定最终方案再交由Executor执行。设计良好的 Reflection 机制，其价值不仅在于修复错误，更在于驱动解决方案在质量和效率上实现阶梯式的提升，这使其成为构建复杂、高质量智能体的关键技术之一。

在执行上，采用执行-反思-优化的循环模式，直至模型任务已经完美解决或者达到最大循环次数再停下。相比Plan-and-Solve，这种架构范式能对已有的方案进行迭代改进，在某些场景例如设计一个算法，生成出来的代码质量更高，但是缺点也很明显，开销比较大，可能导致模型钻牛角尖这些问题还需配合其他方法来解决

记忆与检索

当前的大语言模型虽然强大，但设计上是无状态的。这意味着，每一次用户请求（或API调用）都是一次独立的、无关联的计算。因此需要记忆来存储之前的状态，而记忆又可以分成短期记忆和长期记忆。

  1. 短期记忆：负责处理当前会话的上下文，保证多轮对话的流畅和连贯。一般利用LLM自身的上下文窗口来实现，之前写的ReAct demo就是直接将会话结果注入到prompt然后调用llm，这是最简单的实现方式。相关的策略一般有滑动窗口机制，只保留最近的N轮对话
  2. 长期记忆：Agent能跨会话记住用户的偏好、习惯和历史。一般是通过数据库，文件等方式实现，例如claude.md，向量数据库等

记忆系统的工作过程


记忆系统大致包括这几个流程：

  1. 编码（Encoding）：将感知到的信息转换为可存储的形式
  2. 存储（Storage）：将编码后的信息保存在记忆系统中
  3. 检索（Retrieval）：根据需要从记忆中提取相关信息
  4. 整合（Consolidation）：将短期记忆转化为长期记忆
  5. 遗忘（Forgetting）：删除不重要或过时的信息

RAG

RAG是什么

检索增强生成（Retrieval-Augmented Generation，RAG）是一种结合了信息检索和文本生成的技术。它的核心思想是：在生成回答之前，先从外部知识库中检索相关信息，然后将检索到的信息作为上下文提供给大语言模型，从而生成更准确、更可靠的回答。

因此，检索增强生成可以拆分为三个词汇。检索是指从知识库中查询相关内容；增强是将检索结果融入提示词，辅助模型生成；生成则输出兼具准确性与透明度的答案。

工作流程

一个完整的RAG应用流程主要分为两大核心环节。在数据准备阶段，系统通过数据提取、文本分割和向量化，将外部知识构建成一个可检索的数据库。随后在应用阶段，系统会响应用户的提问，从数据库中检索相关信息，将其注入Prompt，并最终驱动大语言模型生成答案。

上下文工程

什么是上下文工程

总所周知，模型每轮调用的上下文窗口是有限的，而有些场景，例如编写代码，为了编写代码不出错，模型就得知道代码的目的是什么，接口是怎么写的，项目架构是怎样的。这些信息模型得知道，但是如果用之前的办法一股脑塞到上下文中，模型可能会出现幻觉甚至上下文爆炸。因此，从记忆提取的上下文需要经过摘要然后变成提示词传给模型，这一环节就叫上下文工程。上下文工程的“艺与术”，在于从持续扩张的“候选信息宇宙”中，甄别哪些内容应当进入有限的上下文窗口。

怎样是好的上下文工程

一个好的上下文工程目标是：用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。

设计上下文工程通常从这三个方面入手：

  • 系统提示（System Prompt）：语言清晰、直白，信息层级把握在“刚刚好”的高度。
  • 工具（Tools）：工具定义了智能体与信息/行动空间的契约，必须促进效率：既要返回token 友好的信息，又要鼓励高效的智能体行为。
  • 示例（Few-shot）：始终推荐提供示例，但不建议把“所有边界条件”的罗列一股脑塞进提示。

同时，面向长时程任务的上下文工程，有限的上下文窗口无法有效根治上下文污染的情况，那么此时还需用到压缩整合（Compaction）、结构化笔记（Structured note-taking） 与 子代理架构（Sub-agent architectures） 这几种手段

此外，按需检索和渐进式披露也是解决上下文问题的手段之一：

  1. 渐进式披露：给模型提供工具时，不把工具的代码喂给ai，而是给ai一份工具清单并注明什么时候该调用此工具
  2. 按需检索：例如在代码创作中为ai提供glob、grep等原语，让模型自行搜索对应的文件，而不是直接给ai所有代码

一个好的上下文系统通常遵循GSSC（获取- 选择- 结构化- 压缩）流水线设计：

  1. Gather：从多个来源汇集候选信息。这个阶段的关键在于容错性和灵活性。
  2. Select：根据相关性和新近性对候选信息进行评分和选择。这是整个流水线的核心，直接决定了最终上下文的质量。
  3. Structure：将选中的信息组织成结构化的上下文模板。
  4. Compress：对超限上下文进行压缩处理。

智能体通信协议

前面学到，记忆系统是解决模型无法连续对话的问题，上下文是在记忆系统的基础上，解决上下文污染，提示词冗余等问题。而此时，我们的智能体仍面临两大问题：如何让智能体与外部世界高效交互？如何让多个智能体相互协作？

以上两个问题主要通过MCP（Model Context Protocol），A2A（Agent-to-Agent Protocol） ，ANP（Agent Network Protocol） 这三个协议来解决

MCP协议

模型本身是无法调用工具的，同时模型的知识又与模型本身训练的时间有关，无法做到全知全能，因此需要工具来扩展模型的能力。之前的做法是直接为模型编写工具类，这就带来一个问题：每扩展一个工具就要编写一个专门的工具类，这就导致工作量大而且不同开发者编写的工具无法互相兼容等问题。

因此MCP协议诞生了，为了解决这些问题，它提供了一套标准化的接口规范，让智能体能够以统一的方式访问各种外部服务，而无需为每个服务编写专门的适配器。

MCP架构

MCP 协议采用 Host、Client、Servers 三层架构设计，Host层负责接收用户提问并于模型交流，Client层负责与MCP Server建立连接，Server负责工具实现

工作流程

  1. 工具发现阶段：MCP Client 连接到 Server 后，首先调用list_tools()获取所有可用工具的描述信息（包括工具名称、功能说明、参数定义）
  2. 上下文构建：Client 将工具列表转换为 LLM 能理解的格式，添加到系统提示词中。例如：
  3. 工具执行：如果 LLM 决定使用工具，Client 通过 MCP Server 执行所选工具，获取结果
  4. 结果整合：工具执行结果被送回给 LLM，LLM 结合结果生成最终回答

与Function Calling的关系

Function Call（函数调用 / 工具调用） 指的是：让大模型在生成回答时，不直接输出最终文本，而是输出一个“调用外部工具或 API 的请求指令”（通常是JSON格式）。通常需要向模型说明可用的外部函数，包括函数名、功能说明、以及每个参数的类型和含义。模型来判断是否调用工具，若需要则会输出一个约定好的JSON对象，程序接收这个JSON对象后再执行相应的函数，最后将这个结果返回给模型，这就是Function Call的运行流程。本质就是从模型的输出中解析工具名和工具传参，然后调用对应的函数，需要先向模型约定一套输出规范，同时工具的输出也要遵守特定的格式，这就导致每接入一个工具都要编写适配器，工作量很大。

而MCP协议相当于是把这个过程给标准化了，所有支持MCP的工具都会遵循标准的输入输出格式，方便给不同的模型来调用。相比Function Call硬编码约定函数的方式，MCP协议拥有 采用的是外部发现的方式，工具可以缓存在本地，约定的范围扩大到函数+资源+模板

使用MCP

拿hello-agents框架的mcp客户端实现举例，一个mcp客户端主要做三件事：

  1. 连接mcp服务端
  2. 实现list_tools列出mcp服务端的工具
  3. 实现call_tool调用工具 除此之外mcp客户端还支持列出、读取resource和prompt的功能

通过分析mcp协议的实现后其实很好理解mcp的原理，之前设计Function Calling时的流程是：写好工具的实现代码->注册->将工具写到prompt中待模型调用
而mcp是这么做的：将工具都封装到mcp服务器中->模型添加mcp服务器->自动展开为多个独立工具->注册工具待模型调用

关注具体的代码实现，agent连接mcp服务器后会自动展开该服务器的工具然后注册到agent的可使用工具中。对比Function Calling，主要差异点在工具是从外部获取的，只要遵循mcp协议输入输出的工具都可以被接入到agent当中

A2A协议

A2A（Agent2Agent）协议是一个开放标准，旨在让不同来源、基于不同框架构建的AI智能体（Agent）能够相互发现、通信与协作，实现智能体间的点对点协作

构成

包含以下组件：

  1. A2A客户端 (A2A Client)：发起通信的智能体或应用，它代表用户或其他智能体发送请求。
  2. A2A服务器 (A2A Server)：提供服务的智能体，它暴露一个HTTP端点来接收和处理客户端的请求。
  3. 智能体卡片 (Agent Card)：每个A2A服务器都会发布一个JSON格式的“数字名片”，详细描述其身份、能力、技能和访问端点。客户端通过它来发现和了解如何与服务器交互。
  4. 任务 (Task)：一个有状态的工作单元，代表客户端和服务器为达成某个结果而进行的协作。它拥有唯一的ID和明确的生命周期，支持异步执行和状态跟踪。
  5. 消息 (Message)：是客户端和智能体之间单次通信的载体，用于传递指令、上下文、状态更新等过程信息。
  6. 工件 (Artifact)：是智能体在任务执行完成后生成的最终、具体的输出结果，如文档、图片等。

工作流

A2A 请求生命周期是一个序列：代理发现、身份验证、发送消息 API 和发送消息流 API。

与MCP协议的区别

ANP协议

ANP 协议专注于解决大规模、开放网络环境下的智能体管理问题。

关键概念

工作流程


1. 服务的发现与匹配： 首先，智能体 A 通过一个公开的发现服务，基于语义或功能描述进行查询，以定位到符合其任务需求的智能体 B。该发现服务通过预先爬取各智能体对外暴露的标准端点（.well-known/agent-descriptions）来建立索引，从而实现服务需求方与提供方的动态匹配。

2. 基于 DID 的身份验证： 在交互开始时，智能体 A 使用其私钥对包含自身 DID 的请求进行签名。智能体 B 收到后，通过解析该 DID 获取对应的公钥，并以此验证签名的真实性与请求的完整性，从而建立起双方的可信通信。

3. 标准化的服务执行： 身份验证通过后，智能体 B 响应请求，双方依据预定义的标准接口和数据格式进行数据交换或服务调用（如预订、查询等）。标准化的交互流程是实现跨平台、跨系统互操作性的基础。

总而言之，该机制的核心是利用 DID 构建了一个去中心化的信任根基，并借助标准化的描述协议实现了服务的动态发现。这套方法使得智能体能够在无需中央协调的前提下，安全、高效地在互联网上形成协作网络。
